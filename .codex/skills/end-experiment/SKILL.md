# Завершение эксперимента

Используй этот скилл, когда пользователь объявляет текущий эксперимент готовым и просит включить его в `main`.

Это изменяющий удаленный репозиторий процесс. Не применяй его для простого просмотра статуса или проверки результатов.

## Требуемый результат

Текущая ветка эксперимента должна быть синхронизирована с актуальным `origin/main`, проверена, слита отдельным merge-коммитом в локальную ветку `main`, после чего обновленный `main` должен быть успешно отправлен в `origin` без force-push.

## Работа с учетными данными

1. Ищи файл `.env` в корне Git-репозитория. Он должен оставаться локальным и не должен попадать в коммиты.
2. Читай из `.env` только необходимые ключи `GH_TOKEN` или `GITHUB_TOKEN` и, если присутствует, `GITHUB_USERNAME`. Не исполняй `.env` как shell-скрипт и не загружай из него произвольные команды.
3. Никогда не показывай значение токена в выводе, логах, URL, командах итогового отчета или сообщениях пользователю.
4. Перед сетевыми операциями передай токен только через переменную окружения текущего процесса. Для GitHub CLI используй `GH_TOKEN`; если в `.env` задан только `GITHUB_TOKEN`, скопируй его значение в `GH_TOKEN` в памяти процесса.
5. Проверь аутентификацию командой `gh auth status` и настрой Git на использование GitHub CLI командой `gh auth setup-git`. Не записывай токен непосредственно в URL удаленного репозитория.
6. Если `.env`, подходящий токен или `gh` отсутствуют либо аутентификация не проходит, остановись до слияния и push. Сообщи только причину, не раскрывая секрет.

## Порядок действий

1. Найди корень репозитория через `git rev-parse --show-toplevel` и работай только из него.
2. Убедись, что `origin` указывает на ожидаемый GitHub-репозиторий, текущая ветка существует и это не `main`. Запомни ее как `<experiment-branch>`.
3. Проверь `git status --short`. Если есть незакоммиченные или неотслеживаемые файлы, не коммить, не удаляй и не прячь их автоматически: остановись и попроси пользователя сначала привести эксперимент в готовое состояние.
4. Убедись, что `.env` игнорируется Git. Если `git check-ignore .env` не подтверждает игнорирование, остановись и попроси пользователя добавить `.env` в корневой `.gitignore`; сам `.env` не индексируй и не продолжай слияние.
5. Загрузив учетные данные по правилам выше, выполни `git fetch origin main`.
6. На ветке `<experiment-branch>` выполни `git merge --no-edit origin/main`. Не используй rebase и не переписывай историю. При конфликтах не угадывай решение: разрешай только очевидные конфликты в рамках эксперимента; иначе остановись, перечисли конфликтующие файлы и оставь пользователю понятное состояние.
7. Запусти релевантные тесты, линтеры или проверочные команды, уже предусмотренные репозиторием. Если проверки падают, не переходи к `main` и не отправляй изменения.
8. Убедись, что после синхронизации рабочее дерево чистое.
9. Если локальная ветка `main` существует, переключись на нее командой `git switch main` и обнови только fast-forward-командой `git merge --ff-only origin/main`. Если локального `main` нет, создай отслеживающую ветку командой `git switch -c main --track origin/main`. Если существующий локальный `main` расходится с `origin/main`, остановись; не сбрасывай ветку и не переписывай ее автоматически.
10. Слей эксперимент отдельным merge-коммитом: `git merge --no-ff <experiment-branch> -m "Merge experiment <experiment-branch>"`.
11. Еще раз выполни предусмотренные репозиторием проверки уже на итоговом `main`. При ошибке не делай push и сообщи результат.
12. Непосредственно перед отправкой снова выполни `git fetch origin main` и проверь, что `origin/main` является предком текущего `main`. Если удаленный `main` успел измениться, не используй force-push: вернись на `<experiment-branch>`, синхронизируй ее с новым `origin/main`, повтори проверки и только затем заново выполни слияние в обновленный локальный `main`.
13. Отправь результат командой `git push origin main`. Никогда не используй `--force` или `--force-with-lease`.
14. Проверь, что push успешен и `git status --short --branch` не показывает незавершенных изменений или расхождения `main` с `origin/main`.

Не удаляй ветку эксперимента локально или на GitHub без отдельной просьбы пользователя. В финальном сообщении укажи слитую ветку, commit SHA итогового `main`, выполненные проверки и подтверждение успешного push.
